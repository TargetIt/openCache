# GPGPU-Sim Cache Reference — 遗留问题与解答

> 记录时间：2026-05-28

---

## 问题 1：SRAM 读写的时序开销是怎么模拟的？

### 核心机制：`bandwidth_management` 端口模型

GPGPU-Sim 的 cache 不是直接模拟 SRAM 的 bitcell 读取延迟，而是通过 **`bandwidth_management`** 类（`gpu_cache_ref.h:1452-1479`）对两个端口进行占用周期建模：

| 端口 | 用途 | 计数器 |
|------|------|--------|
| **data_port** | 命中时的数据传输 / 脏行驱逐时的写回传输 | `m_data_port_occupied_cycles` |
| **fill_port** | 从下级填充数据到 cache line | `m_fill_port_occupied_cycles` |

### 端口占用周期计算

**data_port**（`gpu_cache_ref.cc:1153-1182`）：

```cpp
case HIT:
    data_cycles = data_size / port_width + ((data_size % port_width > 0) ? 1 : 0);
    m_data_port_occupied_cycles += data_cycles;
    break;
// HIT_RESERVED / MISS 仅在发生脏行驱逐(writeback)时占用 data_port
// SECTOR_MISS / RESERVATION_FAIL 不占用端口
```

**fill_port**（`gpu_cache_ref.cc:1185-1189`）：

```cpp
fill_cycles = atom_sz / data_port_width;  // atom_sz = Sector:32B, Normal:line_sz
m_fill_port_occupied_cycles += fill_cycles;
```

### 每周期释放

每个 `cycle()` 调用都会调用 `replenish_port_bandwidth()`（`gpu_cache_ref.cc:1192-1202`），将两个计数器各减 1。

### `data_port_free()` / `fill_port_free()`

当对应计数器归零时返回 `true`。用户在发送新请求前应检查端口空闲状态。

### 关键点

- **同一个 `data_port_width` 参数同时决定吞吐量（带宽）和延迟**：
  - `data_port_width = 128`（等于 line_sz）→ 命中延迟 = 1 cycle
  - `data_port_width = 32` → 命中延迟 = 4 cycles（128B / 32B）
- **Tag 读取和数据读取没有分开建模**：`tag_array::probe()` 和 `bandwidth_management::use_data_port()` 都在同一个 `access()` 调用中完成，不存在独立的 tag read pipeline stage
- **竞争/仲裁也没有单独建模**：多请求之间的竞争通过 `RESERVATION_FAIL`（MSHR 满 / miss_queue 满）间接体现，但没有独立的仲裁延迟

## 问题 2：Cache line 的 refcnt（引用计数）是否有模拟？

### 直接回答：没有

`cache_block_t`、`line_cache_block`、`sector_cache_block` 中**完全没有 refcnt 字段**。

`line_cache_block`（`gpu_cache_ref.h:174-285`）的全部状态字段：

```
m_status        (INVALID / RESERVED / VALID / MODIFIED)
m_tag / m_block_addr
m_alloc_time / m_last_access_time / m_fill_time
m_readable / m_dirty_byte_mask
m_ignore_on_fill_status / m_set_modified_on_fill / ...
```

没有 `m_refcnt`，没有 `pending_readers`，没有任何形式的并发访问计数器。

### GPGPU-Sim 如何替代 refcnt 机制？

GPGPU-Sim 用了三层机制来替代：

#### 第一层：`HIT_RESERVED` — 阻塞信号

当 line 处于 `RESERVED` 状态时（已分配但未 fill），任何对该 line 的 probe 返回 `HIT_RESERVED`（`gpu_cache_ref.cc:263-266`）。这类似于一个**粗粒度的锁**：line 被"锁定"直到 fill 完成。但它不统计有多少个请求者在等。

#### 第二层：MSHR 条目 — 请求合并

`mshr_table`（`gpu_cache_ref.h:1026-1082`）为每个未完成地址维护一个 `std::list<mem_fetch*>`。当同一地址的第二个请求到达时：
- `mshr_table::probe()` → 返回 `true`（该地址已有未完成条目）
- 如果 `mshr_table::full()` 返回 `false`（条目未超过 `m_max_merged`）
- 调用 `mshr_table::add()` 将新请求追加到 list 中
- `access()` 返回 `MSHR_HIT`（而不是再发一次下级请求）

当 fill 完成时，`mshr_table::mark_ready()` 将该地址加入 `m_current_response` 列表，`next_access()` 逐个弹出。**每个合并的请求都会通过 `next_access()` 独立返回**，确保不发丢。

#### 第三层：`extra_mf_fields::pending_read` — 多 sector 拆分计数

这不是 line 级别的 refcnt，而是**一个请求拆分后等待子请求返回的计数器**：

```cpp
// gpu_cache_ref.h:1411-1415
pending_read = m_config.m_mshr_type == SECTOR_ASSOC
                   ? m_config.m_line_sz / SECTOR_SIZE  // 例如 128/32 = 4 个 sector
                   : 0;
```

当 SECTOR_ASSOC MSHR 处理一个非 sector 缓存（如 normal L1 → sector L2）发来的请求时，这个请求会被拆成多个 sector 粒度子请求。`pending_read` 跟踪还有几个子请求没回来。全部回来后，`baseline_cache::fill()` 才组装原始请求并 `mark_ready`。

### 硬件 refcnt 在 GPGPU-Sim 中的缺失意味着什么？

真实硬件中：
```
hit-test 阶段:  refcnt++    (占用 tag SRAM)
读 SRAM 阶段:   refcnt--    (占用 data SRAM)
驱逐条件:       refcnt == 0  (无人正在读此行)
```

GPGPU-Sim **不区分这两个阶段**。它的 `HIT` 返回意味着"数据立即可用"，在一个 `access()` 调用中同时完成了 tag check 和 data port 占用。没有 refcnt 意味着：
- 无法模拟"一行在被驱逐时正被读取"的冲突
- 无法模拟多个 reader 同时从同一行读取的 SRAM bank 冲突
- 无法模拟 tag pipeline 和 data pipeline 之间的深度差异

## 问题 3：发请求和读数据是否分开？

### 是分开的，但分法取决于 access() 的返回值

**HIT 路径**：请求和读数据在同一个 `access()` 调用中完成。

```cpp
// HIT: 数据立即可用
auto status = cache.access(addr, &mf, time, events);
if (status == HIT) {
    // 数据已经"在 cache 中" — 延迟仅由 data_port_width 决定
    record_hit(&mf, time);
}
```

`HIT` 返回时，cache 内部已经完成了 tag probe → 确认 VALID/MODIFIED → `use_data_port()` 记录带宽占用的全部流程。用户不需要再调任何其他函数来"读数据"。

**MISS / SECTOR_MISS / MSHR_HIT 路径**：请求入队和读数据是**两个独立阶段**：

```cpp
// 阶段 1: 发请求 (access)
auto status = cache.access(addr, &mf, time, events);
// → MISS: 请求已入 miss_queue + MSHR，等待 fill

// 阶段 2: 推进流水线 (cycle + fill)
cache.cycle();                      // 将 miss_queue 推向下级
lower_mem->push(mf);                // 下级处理
cache.fill(&returned_mf, time);     // 数据返回，更新 tag + MSHR ready

// 阶段 3: 读数据 (access_ready / next_access)
while (cache.access_ready()) {
    mem_fetch *ready = cache.next_access();  // 取回完成的请求
    record_complete(ready, time);
}
```

### 为什么伪代码中 access_ready()/next_access() 是单独的步骤？

因为 `mem_fetch` 在 MISS 后经历了完整的异步流水线：

```
access() → miss_queue → cycle() → lower_mem → fill() → MSHR ready → next_access()
  (发)                                                              (取)
```

`access_ready()` / `next_access()` **只服务于 MISS 路径**。对于 HIT，请求不走 MSHR，也不会出现在 `access_ready()` 中。

### 总结

| access() 返回值 | 数据立即可用？ | 需要 access_ready()/next_access()？ |
|----------------|:------------:|:---------------------------------:|
| `HIT` | 是 | 否 |
| `HIT_RESERVED` | 否 | 是 |
| `MISS` | 否 | 是 |
| `SECTOR_MISS` | 否 | 是 |
| `MSHR_HIT` | 否 | 是 |
| `RESERVATION_FAIL` | N/A（请求被拒绝） | 否（需重试） |

## 问题 4：access() 返回值的各类状态含义

### 全部 6 种状态

```cpp
enum cache_request_status {
  HIT = 0, HIT_RESERVED, MISS, RESERVATION_FAIL, SECTOR_MISS, MSHR_HIT
};
```

### HIT

**触发条件**（`tag_array::probe()`, `gpu_cache_ref.cc:267-277`）：
- 标签匹配
- 且状态为 `VALID`
- 或状态为 `MODIFIED` 且（读取且 `is_readable`）或写入

**用户动作**：数据立即可用。延迟 = `ceil(data_size / data_port_width)` 周期。直接消费数据，不需要等 `access_ready()`。

---

### HIT_RESERVED

**触发条件**（`gpu_cache_ref.cc:263-266`）：
- 标签匹配
- 但行（或 sector）的状态为 `RESERVED`（已分配行但 fill 还没完成）

**用户动作**：数据不可用。必须等待 fill 完成后通过 `access_ready()` / `next_access()` 取回。

**出现的典型场景**：
- 前一个 MISS 已分配了该行，fill 还在路上
- 另一个请求正好命中同一行（MSHR 会合并这两个请求）

---

### MISS

**触发条件**（`gpu_cache_ref.cc:324-332`）：
- 在 set 中没有找到匹配的 tag
- 且 set 中存在 INVALID 行或可替换行（`all_reserved == false`）

**用户动作**：请求已接受。等待 `cycle()` → 下级返回 → `fill()` → `access_ready()` / `next_access()`。

---

### SECTOR_MISS

**触发条件**（`gpu_cache_ref.cc:279-281`）：
- 仅 `m_cache_type == SECTOR` 时可能
- 标签匹配（行有效），但**特定 sector** 的状态为 `INVALID`
- 或者标签匹配，sector 为 `MODIFIED` 但读取且 `is_readable == false`

**用户动作**：与 MISS 相同。区别是只填充缺失的 sector，不是整行。

---

### MSHR_HIT

**触发条件**（`send_read_request()`, `gpu_cache_ref.cc:1336-1344`）：
- `mshr_table::probe(block_addr)` 返回 `true` — 该地址已有未完成的 MSHR 条目
- `mshr_table::full(block_addr)` 返回 `false` — 该条目还有合并空间（< `m_max_merged`）

**用户动作**：请求已合并到已有 MSHR 条目。不需额外动作。当原始条目完成时，此请求随 `next_access()` 返回。

---

### RESERVATION_FAIL

**触发条件**：5 种子原因（`gpu_cache_ref.h:61-68`）：

| 子原因 | 触发条件 | 含义 |
|--------|---------|------|
| `LINE_ALLOC_FAIL` | Set 中所有行都处于 RESERVED 状态，无 INVALID 行也无非 RESERVED 的可替换行 | 所有行都在等 fill，无法分配新行。仅在 `ON_MISS` 分配策略下发生 |
| `MISS_QUEUE_FULL` | `m_miss_queue.size() + num_miss >= m_miss_queue_size` | 下级发送队列已满，无法接受新的 miss 请求 |
| `MSHR_ENRTY_FAIL` | MSHR 表已满（`m_data.size() >= m_num_entries`），且当前地址没有已有条目可合并 | 无空闲 MSHR 条目 |
| `MSHR_MERGE_ENRTY_FAIL` | MSHR 条目存在（`probe()` 返回 true），但合并数已达上限 `m_max_merged` | 无法合并更多请求 |
| `MSHR_RW_PENDING` | 对一个地址发起写请求，但 MSHR 中已有该地址的读请求（`is_read_after_write_pending`） | 写后读冲突保护，防止破坏正在读取的数据 |

**用户动作**：请求**完全被拒绝**（无行分配、无 MSHR 条目、无 miss_queue 入队）。**必须在后续周期重试**。持续 RESERVATION_FAIL 意味着需要增大对应资源（MSHR 条目数、miss_queue 大小、associativity）。

**如何诊断**：通过 `cache_stats::print_fail_stats()` 按原因分类打印失败统计：

```cpp
cache.get_stats().print_fail_stats(stdout, 0, "L1D");
// 输出: LINE_ALLOC_FAIL: X次, MISS_QUEUE_FULL: Y次, ...
```

### 状态机流转总览

```
INVALID ──[allocate]──→ RESERVED ──[fill]──→ VALID ──[write]──→ MODIFIED
   ↑                        │                    │                   │
   │                        │                    │                   │
   └──[invalidate]──────────┴────────────────────┴───[flush/writeback]──┘

probe 返回值:
  INVALID  → MISS
  RESERVED → HIT_RESERVED
  VALID    → HIT
  MODIFIED → HIT (写命中时原地修改; 读命中时需 is_readable)
```
